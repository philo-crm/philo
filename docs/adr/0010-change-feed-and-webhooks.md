# 0010 — One change feed for the live app and for webhooks

- **Status:** Accepted
- **Date:** 2026-10-25

## Context

The in-app notification stream (`GET /api/v1/push/live`, DESIGN.md
Notifications) proved that a Server-Sent Events stream over `fetch` works from
the PWA with its bearer token. It carries one thing: a new lead, as a
notification to show. Two more needs sit right next to it:

- **The PWA goes stale.** A lead an agent moves, or one a form files, does not
  show on an open board until someone reloads. With one or two people and an
  agent working the same funnel, the board is wrong more often than it is right.
- **Nothing outside Philo hears about a change.** An automation that should
  react to a lead reaching "Qualified" has to poll. DESIGN.md deferred webhooks
  as a *third notification channel* beside push and email; this is a different
  need — integration, not notification — and agents ask for it by name.

Both are "tell someone a lead changed". The question is whether they share
one source of truth for what a change is.

## Options considered

### Option A — the PWA polls; webhooks hang off each route

- No new stream.
- Polling is either slow or wasteful, and each route that mutates a lead would
  carry its own webhook call — a route added later forgets it, and the two
  surfaces drift on what counts as a change.

### Option B — webhooks from the `lead_events` timeline

- The timeline is already written for every change, in the same transaction.
- It is a log for people, not a contract: deletion erases it by design
  (DESIGN.md, Erasure), a no-op stage move writes nothing, and contact edits
  are not on it at all. Building a delivery queue on top of it would make its
  shape a public API.

### Option C — one in-process change feed, two consumers

- Every route that commits a change to a lead (or to a funnel's stages)
  publishes one typed event to an in-memory feed after the commit. The live
  stream forwards it to open tabs; the webhook dispatcher posts it to each
  matching registration.
- Delivery is best-effort and in memory, like push: a process restart drops
  retries in flight. One instance per business means one process, so an
  in-memory bus has no fan-out problem to solve.

## Decision

**Option C.**

**Events.** `lead.created`, `lead.updated`, `lead.stage_changed`,
`lead.deleted`, and `funnel.changed` (stages added, renamed, reordered or
removed; a funnel renamed). Each carries an id, the type, the time, the
funnel it belongs to, and — for a lead event — the lead record without its
timeline. `lead.deleted` carries the id and nothing else: an event that named
the person would be a copy of what was asked to go. Quarantined leads publish
nothing; promoting one out of spam publishes `lead.created`, matching when
email and push fire for it.

**Live stream.** `GET /api/v1/events` (optional `?funnel=<id>`), the same SSE
format and the same 15-minute reconnect as `/push/live`. The PWA holds it open
on the board, the lead list and a lead's own screen and refetches what an
event touches. The notification stream stays as it is; it answers a different
question.

**Webhooks.** A registration is a URL, an optional funnel (none means every
funnel), and an optional list of event types (none means all). Created through
`/api/v1/webhooks` by any credential — ADR-0007 — and listed, tested and deleted
the same way. Each delivery is a `POST` of the event as JSON, signed:

- `X-Philo-Signature: sha256=<hex>` — HMAC-SHA256 over `<timestamp>.<body>`
  with the registration's secret, the timestamp also sent as
  `X-Philo-Timestamp`, so a receiver can refuse a replay.
- The secret is generated by Philo and shown once, at creation, like an API key.
  It is stored as-is; signing needs it.
- A 2xx is success. Anything else, a timeout (10 s) or a network failure is
  retried twice more, after 10 s and 60 s. Redirects are not followed.
  The last outcome is kept on the registration for the settings screen.

Only `http` and `https` URLs are accepted. Philo does not try to keep a
registration off private addresses: the person registering one already holds
the instance's full authority, and a local automation (a workflow tool on the
same host) is a legitimate target.

## Consequences

- The board, the lead list and an open lead update themselves.
- Integrations react to changes without polling, scoped to the funnel they
  care about.
- A route that mutates a lead now has a second duty — publish — and a test
  for each publishing route keeps that honest.
- Webhook delivery is at-most-a-few-times and can be lost on restart. A
  receiver that must not miss a change still reconciles against the API; the
  event id lets it ignore a retry it already handled.
- Revisit with a durable outbox if an operator depends on webhooks for
  something that cannot be reconciled.
